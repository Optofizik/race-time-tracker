# Formatter Phase — Final Competition Protocol

## 1. Objective

Add a .NET 10 Console application to the existing `RaceTimeTracker` solution. The application converts a competition passage CSV into a final protocol.

The formatter must:

- accept the source CSV file path as a command-line argument;
- validate and read the passage records produced by the WPF application;
- select the last recorded passage for each runner as that runner's finish time;
- sort runners by finish time in ascending order;
- assign a sequential place number;
- write the result beside the source file as `<original_file_name>_formatted.csv`;
- report errors clearly and return a meaningful process exit code.

Example invocation:

```powershell
dotnet run --project RaceTimeTracker.Formatter -- competition_6578.csv
```

For `competition_6578.csv`, the output is `competition_6578_formatted.csv` in the same directory.

## 2. Scope

### In scope

- One input file per invocation.
- CSV files with the header `start_number,time_elapsed`.
- Multiple passage records for the same runner.
- Preservation of start numbers as text, including leading zeroes.
- Duration parsing compatible with files generated by the WPF application.
- Deterministic ordering and place assignment.
- Safe output creation and replacement.
- Automated tests for parsing, selection, sorting, formatting, and failures.

### Out of scope

- Changes to the WPF application or its CSV-writing contract.
- Participant names, categories, age groups, teams, or disqualifications.
- Editing or repairing malformed source data.
- Combining multiple competition files.
- Interactive file selection or a graphical interface.
- Live monitoring of a competition file.
- PDF, spreadsheet, or printable-report generation.
- Publishing the protocol to a server or cloud service.

## 3. Recommended technical baseline

- **Framework:** .NET 10
- **Application type:** Console application
- **Language:** C# with nullable reference types enabled
- **Target framework:** `net10.0`
- **CSV implementation:** a small RFC 4180-compatible reader/writer or a deliberately selected CSV package
- **Culture:** invariant culture for duration parsing and formatting
- **Testing:** the test framework already used by the solution; otherwise xUnit

## 4. Command-line contract

### Invocation

```text
RaceTimeTracker.Formatter <csv-file>
```

Rules:

- Exactly one positional argument is required.
- The argument may be an absolute or relative path.
- Resolve a relative path against the current working directory.
- The source must exist, be a file, and have a `.csv` extension, compared case-insensitively.
- Surrounding quotes are handled by the shell and are not part of the path.
- The formatter must not prompt for missing input, so it remains scriptable.

### Exit codes

- `0`: protocol created successfully.
- `1`: invalid command-line usage.
- `2`: source file not found or inaccessible.
- `3`: invalid CSV structure or record value.
- `4`: output file could not be written.
- `10`: unexpected application failure.

On success, print the full output path and the number of ranked runners. On failure, write a concise actionable message to standard error. Do not print a stack trace during normal use.

## 5. Input contract

The input is a comma-delimited UTF-8 CSV file:

```csv
start_number,time_elapsed
112,00:46:12.200
103,00:48:15.000
112,01:02:41.350
```

Requirements:

- The header must contain exactly `start_number,time_elapsed` in that order.
- A UTF-8 byte-order mark may be accepted on the first header field.
- Blank physical lines may be ignored.
- Every non-blank data row must contain exactly two fields.
- Fields must be read with standard CSV quoting rules; splitting lines with `string.Split(',')` is insufficient.
- Trim surrounding unquoted whitespace before validation.
- `start_number` is non-empty text and is written without numeric conversion, preserving leading zeroes.
- `time_elapsed` is a non-negative duration.
- Duration parsing uses invariant culture and accepts the WPF contract `HH:mm:ss.fff`, including total hours above 23. For compatibility with the task wording, `m:ss`, `m:ss.f...`, `h:mm:ss`, and `h:mm:ss.f...` are also accepted.
- Minutes and seconds must be in the range `0`–`59` whenever an hours component is present; seconds must always be in the range `0`–`59`.
- The entire file must be validated before an output file is replaced.

The example in the request (`0:46:12.2`) contains hours, minutes, and seconds even though the prose says “minutes:seconds.” Supporting both shapes resolves that inconsistency and remains compatible with the existing WPF output.

Malformed headers, malformed quoting, missing fields, invalid durations, and negative durations are fatal. Error messages should include the source line or record number where possible.

## 6. Protocol-generation rules

### FR-01 — Select the latest record per runner

- Treat runner identity as the exact normalized `start_number` text after surrounding whitespace is removed.
- Compare start numbers using ordinal, case-sensitive comparison. The current producer permits digits only, but the formatter must not silently merge distinct textual identifiers.
- “Latest” means the last valid record for that start number in source-file order, not the greatest duration.
- A later record replaces the earlier selected record for the same runner.

Example:

```csv
start_number,time_elapsed
112,00:46:12.200
103,00:48:15.000
112,01:02:41.350
```

Runner `112` finishes with `01:02:41.350`.

### FR-02 — Sort finishers

- Sort selected records by parsed elapsed duration in ascending order.
- For equal durations, sort by `start_number` using ordinal comparison to make output deterministic.
- Sorting uses the parsed duration value, never a string comparison.

### FR-03 — Assign places

- Assign sequential positions `1..N` after sorting.
- Equal finish times still receive distinct sequential places; the deterministic start-number tie-breaker decides their order.
- Competition-style shared places or tie rules are out of scope until explicitly required.

### FR-04 — Write the final protocol

Write a comma-delimited UTF-8 CSV file with this exact header:

```csv
start_number,time_elapsed,place
112,00:46:12.2,1
103,00:48:15,2
```

Rules:

- Build the output name from the source path using `<name-without-extension>_formatted.csv`.
- Place the output in the source file's directory.
- Never allow the computed output path to equal the input path.
- Write start numbers using standard CSV escaping.
- Format durations canonically as total-hours `H:mm:ss`, adding a fractional part only when non-zero.
- Preserve parsed sub-second precision up to seven decimal places and trim trailing fractional zeroes. For example, `00:46:12.200` becomes `0:46:12.2` and `00:48:15.000` becomes `0:48:15`.
- Do not wrap total hours after 24 hours.
- Use comma delimiters and CRLF line endings regardless of operating-system culture.
- If the source contains only a valid header, create an output containing only the protocol header.

Write to a temporary file in the destination directory and replace/move it to the final name only after all rows have been written successfully. An existing formatted file may be replaced only by a completely generated new result. Clean up a temporary file after a handled failure when possible.

## 7. Architecture and responsibilities

### Domain

`PassageRecord`

- `StartNumber`
- `Elapsed`
- `SourceOrder`

`ProtocolRecord`

- `StartNumber`
- `Elapsed`
- `Place`

Domain/application rules:

- start number cannot be empty;
- elapsed time cannot be negative;
- source order identifies the last occurrence;
- place is a positive integer.

### Application

`ProtocolFormatter`

- accepts passage records;
- selects the final record for each runner;
- orders finishers;
- assigns places;
- returns protocol records without performing file I/O.

`FormatterApplication`

- coordinates input reading, transformation, and output writing;
- ensures the source is fully validated before output replacement;
- returns a typed result suitable for mapping to an exit code.

### Infrastructure

`IPassageCsvReader`

- reads and validates the input header and records;
- reports useful record-location errors;
- parses durations using invariant rules.

`IProtocolCsvWriter`

- writes the exact output schema;
- escapes CSV fields;
- formats elapsed durations canonically;
- performs safe temporary-file replacement.

### Console entry point

`Program`

- validates argument count and resolves the source path;
- invokes the application workflow;
- prints success or failure information;
- maps known failures to documented exit codes;
- catches unexpected exceptions at the process boundary.

## 8. Error handling

Handle these conditions explicitly:

- no argument or more than one argument;
- invalid path syntax;
- missing source file;
- source path refers to a directory;
- unsupported file extension;
- source file cannot be read or changes during processing;
- empty file or incorrect header;
- malformed CSV quoting or wrong field count;
- empty start number;
- empty, negative, overflowing, or malformed elapsed duration;
- destination directory is not writable;
- output file is locked;
- temporary-file creation or final replacement fails.

Operational rules:

- Do not leave a partially written final protocol.
- Do not replace an existing valid output when input validation fails.
- Include the relevant full path in file-system errors.
- Include a record number in data errors when available.
- Avoid leaking internal stack traces to standard output/error; retain exception details for debugger diagnostics.

## 10. Test scenarios

Automated coverage should include:

1. One passage produces one runner in place 1.
2. Multiple runners are ordered by parsed duration rather than source order or duration text.
3. Multiple passages for a runner select the last source record, even when its elapsed value is lower than an earlier record.
4. Leading-zero start numbers remain unchanged and distinct from their numeric equivalents.
5. Equal elapsed values use ordinal start-number ordering and sequential places.
6. Fractional seconds are parsed, sorted, and formatted without unnecessary trailing zeroes.
7. Durations longer than 24 hours do not wrap.
8. A header-only input creates a header-only output.
9. Quoted fields are parsed and escaped correctly.
10. BOM and CRLF input is accepted.
11. Incorrect headers, wrong field counts, blank start numbers, and invalid durations fail with record context.
12. Missing or extra command-line arguments return exit code `1`.
13. A missing source returns exit code `2`.
14. Invalid data returns exit code `3` without replacing an existing output.
15. A locked or unwritable destination returns exit code `4` without a partial final file.

## 11. Manual acceptance checks

1. Create `competition.csv` with repeated start numbers and run the formatter using a relative path.
2. Confirm `competition_formatted.csv` is created beside the input.
3. Confirm it contains exactly one record per distinct start number.
4. Confirm the selected record is the last input occurrence for each runner.
5. Confirm records are ordered by elapsed time and places run from 1 through the runner count.
6. Confirm leading zeroes in start numbers are preserved.
7. Run using an absolute path containing spaces and confirm the output path is correct.
8. Run again after changing the input and confirm the old output is replaced completely.
9. Supply malformed input and confirm the command fails clearly without modifying the previous valid output.
10. Run with no argument and with a nonexistent file and confirm the documented non-zero exit codes.

## 13. Assumptions requiring product confirmation before later phases

- The last CSV occurrence is authoritative for a runner's finish time.
- Every runner appearing in the input is considered a finisher.
- Equal times receive distinct sequential places rather than shared places.
- Ordinal start-number ordering is the tie-breaker.
- The formatter may replace an existing `_formatted.csv` file safely.
- Both the WPF `HH:mm:ss.fff` duration shape and shorter minute/second forms should be accepted.
- Output uses canonical total-hours formatting with trimmed fractional zeroes.
- A valid header-only input is a successful empty protocol.
